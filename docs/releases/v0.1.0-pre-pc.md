# Aetheris v0.1.0-pre-pc — Release Candidate Notes

**Release class:** `REPOSITORY_PRE_PC`  
**Candidate status:** prepared, not yet published  
**Candidate baseline:** `fd180fb4b41abd29e92d5ca0e4eac6027a8ba291`  
**Final release commit:** resolve at publication from protected `main`  
**Physical-machine status:** `BLOCKED_PENDING_HARDWARE`

This is the first formal release-candidate narrative for the Syntra × Aetheris platform. It describes repository-side engineering maturity only. It does **not** claim that the complete platform has been validated on the owner's target physical PC.

## Highlights

- Repository roadmap completed through **Stage 34 / 34**.
- Protected `main` with pull-request governance and required validation gates.
- Java 21 / Spring Boot distributed backend surfaces with API gateway, identity, user, audit and orchestrator services.
- React + TypeScript dashboard and reproducible local demo path.
- PostgreSQL, Redis and RabbitMQ integration foundations.
- OpenTelemetry, Prometheus, Grafana, Loki and Tempo observability path.
- Local-first AI orchestration model where replaceable models are workers rather than policy authority.
- Aetheris Reach Layer v1 with 15 external channel families, preferred/fallback backend modeling, governed routing, doctor reporting and non-mutating install planning.
- Reach v1 truthfully exposes only the existing governed GitHub API backend as implemented; web/social/video/RSS adapters remain `ADAPTER_REQUIRED` until their execution bridges are built and validated.
- Reasoning, verification, digital-twin, automation, governance and PC-care repository foundations.
- Deterministic owner policy, scoped approvals, emergency precedence and evidence-first completion semantics.
- Dependency lockdown, CodeQL, release-hardening, compatibility freeze and two-pass reproducible-build evidence.
- Community, support, security, contribution, changelog and release-readiness documentation.

## Safety and governance boundaries

The following remain non-negotiable for this release class:

- deterministic owner policy outranks model recommendations;
- `ALLOW` means eligible to execute, not proof that execution occurred;
- success requires verification evidence or an explicit `UNVERIFIED` result;
- emergency precedence remains `STOP > TAKE_CONTROL > PAUSE > NORMAL`;
- `ZERO-COST` blocks configured billable/non-zero-cost fallback paths;
- `PRIVATE` constrains protected content to approved local paths unless an exact owner/policy override permits otherwise;
- live-money execution, withdrawals and transfers remain outside the default trusted AI path;
- hosted CI is repository evidence, not physical-PC validation.

## Known limitations

This candidate intentionally does not claim validation of:

- WSL2 or virtualization on the final owner PC;
- Docker Desktop/runtime behavior on that machine;
- RTX GPU acceleration or local-model throughput;
- thermal, storage or long-duration resource behavior;
- microphone/speaker/voice hardware;
- browser, phone or device-control integrations on the real machine;
- social/web/video/RSS Reach adapters that are still marked `ADAPTER_REQUIRED`;
- browser cookies, authenticated platform sessions or upstream CLI behavior on the target PC;
- unrestricted privileged host execution;
- production deployment readiness outside the declared repository scope.

Physical-PC validation remains pending.

## Publication checklist

Before creating the GitHub release:

1. merge the final release-preparation changes through protected `main`;
2. record the exact final `main` SHA here and in the GitHub release notes;
3. confirm all stable release gates are green on that SHA;
4. confirm `README.md` still reports `Stage 34 / 34`, `BLOCKED_PENDING_HARDWARE`, and that Physical-PC validation remains pending;
5. decide the software-license strategy or explicitly retain the no-license state without claiming open-source reuse rights;
6. create an immutable `v0.1.0-pre-pc` tag on that exact `main` commit;
7. mark the GitHub release as a **pre-release**;
8. preserve this truth boundary in the published notes.

The canonical product/safety contract remains `docs/master-build-spec.md`.
