# Identity-issued signed JWT contract across Gateway, User and Audit

**25 October 2026 — explicitly test-only cross-module authentication verification, stacked after PR #270.**

## Why
Previous PR #267 added independent signed-JWT User/Audit filters, PR #268 hardened numeric UID parsing, PR #269 exercised live loopback User/Audit HTTP, and PR #270 aligned Gateway ADMIN role, scope and Authorization-header rules. Each previous test generally minted a test JWT independently in the consumer test module. That does NOT prove real **Identity JwtService.issue** produces mutually accepted wire tokens, particularly given signer key-strength-driven HMAC algorithm selection, JSON claim numeric types, role/scope vocabulary and required iat.

## Four-module contract in one CI runner
The workflow `.github/workflows/identity-issued-jwt-contract.yml` runs on both Ubuntu 24.04 and Windows Server 2022 in this explicit order:

1. Execute **production Identity `JwtService.issue(IdentityAccount)`** from a JUnit test using synthetic ADMIN (account 42), DEVELOPER (43), and API_CONSUMER (44) accounts, with `ReflectionTestUtils.setField` only to supply fake persisted IDs. It also uses the same real issuer with a negative expiry and corrupts the signature of one real issued JWT. All five tokens are saved in the **temporary CI workspace only**, under `identity-service/target/identity-jwt-contract`; no tokens are committed, uploaded as artifacts or printed.
2. Confirm each expected token file exists and contains three JWT segments, with test-only marker `IDENTITY_ISSUER_DIRECT_JWT_CONTRACT_V1`, without revealing JWT bytes.
3. Execute the actual **Gateway `JwtAuthenticationFilter`** against those same Identity-issued token bytes, demonstrating ADMIN User/Audit read acceptance, DEVELOPER/API_CONSUMER administrative denial, expired/bad-signature denial, signed identity propagation without trusting spoofed request headers and API_CONSUMER access to `orchestrator:read` (Gateway filter in-process, not a deployed HTTP proxy).
4. Start actual **User** and **Audit** embedded Spring Boot application HTTP servers on random ports. Send real `HttpClient` requests to the live loopback filters using those *unchanged* Identity-issued JWT bytes. ADMIN is accepted (User GET 200, mocked User DELETE 204, Audit GET 200); nonadmins are 403 despite forged ADMIN headers; expired/signature-altered tokens and anonymous calls are 401. H2 test-only storage, disabled AMQP listeners, `@MockitoBean` business services and isolated synthetic email addresses avoid production data or writes.

The tests are named `*IT` to avoid silently expanding default Surefire test runs: this CI **explicitly selects** each exact class with `-Dtest=IdentityIssuedJwtContractIT`, so missing issuer files cannot be skipped. The test key matches the existing **literal test-only** User/Audit fixture secret; Identity actually signs with its production implementation. This verifies compatibility across **all three independent verifiers on the same test HMAC key** without writing a separate JWT issuer or copying hand-crafted role scopes into consumer tests.

## Strict limits
- These are real signed tokens generated by production Identity library logic, but do not represent live logged-in users or an actual Identity `/api/auth/login` HTTP request with persisted data.
- Gateway is checked at its real JWT `GlobalFilter` **in-process** with mocked `GatewayFilterChain`, not through a live Gateway reverse proxy. User and Audit use live, isolated loopback HTTP.
- No Docker Compose, Redis, PostgreSQL, RabbitMQ, public network, Kubernetes or customer accounts are used. The HMAC secret is a constant **for synthetic CI only**. Real secrets are never handled.
- Cryptographic compatibility and signed role consistency are not sufficient for full enterprise authorization: missing issuer/audience binding, object ownership/tenant model, revocation/key rotation, service workload identity and inter-container direct access probes remain open in issue #251.
- All parent stacked PRs stay draft/unmerged. This test DOES NOT close Stage45 NO_GO, any of the nine enterprise release gates, E3 autonomous website coding gates or E4–E9. No production deployment or protected-main changes.

**Quality gate:** a successful exact-head GitHub Actions run on *both* OSes with four explicitly executed modules. If any test fails, record its actual outcome and fix the test/app wiring rather than changing JWT authorization rules to make the result green.
