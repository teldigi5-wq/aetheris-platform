## Scope and trust flow
- The server-side User service already obtains a UUID tenant identifier from a separately authenticated/signed JWT and persists it on `users.tenant_id`. Tenant-scoped User create/delete now publishes that same **stored User entity tenantId** through its typed publisher overload; client headers, JSON body or arbitrary record IDs cannot override it.
- Legacy global administrator User mutations publish event messages without `tenantId`; historical audit records also retain a **NULL tenant_id**. No inferred ownership, backfill, or cross-table ID matching.
- Audit service extends its `UserDomainEvent` DTO to contain optional `UUID tenantId`, validates any present event tenant against the canonical lowercase UUID format, and stores it in the additive Flyway V2 `audit_events.tenant_id` UUID column with a partial index. Missing tenant remains NULL, and malformed tenant fields raise an explicit no-requeue rejection instead of infinite RabbitMQ re-delivery. The existing global `GET /api/events` remains strictly ADMIN-only at BOTH Gateway and backend. No tenant-facing audit API has been created.
- The new workflow includes isolated publisher/consumer and service provenance tests, additive Flyway schema/legacy-null verification through actual startup, and repeats the previous real 79-check end-to-end security suite. New end-to-end assertions require separate account A/B event tenant IDs on both create and delete and confirm historical global event attribution remains NULL.

## High-priority unresolved security and reliability gates
- **Broker publisher trust is NOT established.** Current RabbitMQ clients may share a broker credential and an event on the queue is not cryptographically bound to a verified User publisher. A malicious authorized-to-publish producer could forge `tenantId`. The new `tenant_id` is metadata for existing ADMIN-only investigation, **not an authorization input or compliance-grade provenance guarantee**. Need role-separated producer/consumer credentials, namespace/vhost isolation, transport mTLS/TLS, routing ACL and verified producer identity before using these fields to grant tenant-level audit access.
- **Dead-letter strategy is incomplete.** Explicit no-requeue rejection prevents poison redelivery but an operator-controlled DLQ, monitoring and incident process must be added before production. The existing durable queue topology cannot be changed blindly: RabbitMQ will reject incompatible queue argument changes.
- **Outbox guarantee is not solved.** User service still publishes events inside an open JDBC transaction; rollback can produce ghost audit events, and broker failures can cause DB/event divergence. Use transactional outbox, idempotent replay and reconciliation with failure injection before Stage45.
- **Legacy schema migration/rollback** for Identity/User and the Flyway Audit V2 must be reviewed against production snapshots and backups. The hosted suite uses disposable PostgreSQL only. Event idempotence uses the existing `event_id` uniqueness, not proof of exactly-once end-to-end delivery.
- A single account's UUID is not an organization tenant membership graph; multi-member tenant organizations, data sharing, tenant-scoped Audit reads, per-tenant email uniqueness, reliable revocation and enterprise security audit requirements remain unimplemented. Production PKI, Redis AUTH, DB roles, image SCA, CNI, secrets/rotation, independant attestations and source/license rights remain blocked.
