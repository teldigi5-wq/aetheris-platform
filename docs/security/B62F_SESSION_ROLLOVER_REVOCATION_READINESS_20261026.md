# B62-F — Refresh session rollover and emergency-revocation readiness

**2026-10-26 — review-only stacked draft**. Base: B62-E PR #300, exact green CI head `76a3ecbf30c99b7bdc1f4b81a195fc9b0f0f0cb9`. This is an isolated verification slice, **not a production revocation feature**.

## Concrete change

The Identity `RefreshTokenService` constructor now refuses a configured refresh-token lifespan of less than one second or greater than 604,800 seconds (7 days). Default remains 604,800 seconds. The secret is still generated from 32 bytes of `SecureRandom`, stored only as a SHA-256 token hash, and rotated with the existing database `revokeIfActive(...)` claim. No new JPA schema or auth route, production secret, or administrative endpoint has been introduced.

The new JUnit test uses an explicitly mocked repository, two independent synthetic refresh sessions, a simulated service reconstruction using the same in-memory repository state, and a genuinely signed synthetic HMAC access JWT. It establishes that logout revokes the **presented refresh token only**, that a distinct refresh session may still rotate after the simulated restart, and that logout does **not** revoke already-issued stateless JWTs. It does **not** claim physical database persistence, cross-node atomicity or production failover verification. Existing unit tests separately guard token-claim races.

## Operator-controlled rollover and rollback checklist — NEVER execute in production from CI

1. **Owner approval / inventory:** obtain explicit owner approval, independent security review, and the same verified source and configuration inventory for Identity, Gateway, User and Audit. Identify both public `kid` labels, previous-key cutoff UTC, current access-token `iat` to `exp` cap, browser-cookie policy and refresh DB migration state. Inventory metadata only; no real production keys or customer refresh tokens may be copied to testing.
2. **Synthetic session continuity drill:** test two isolated sessions A/B. Confirm login, refresh rotation and one-time replay denial; browser refresh cookie remains `HttpOnly; Secure; SameSite=Strict`. Log out session A and explicitly confirm that session B remains valid according to current design, while its access JWT stays valid until expiration. This is *session-scoped refresh logout*, not a global kill switch.
3. **Safe key overlap:** the issuer alone holds its private signing key; verifiers hold only pinned 3072-bit-or-stronger RSA public material. When changing `kid`, use preapproved, consistent issuer/verifier configuration with a previous-key cutoff of at most one hour. After the previous-key cutoff, verify denial in the same Gateway/User/Audit processes and remove previous-key trust in a controlled follow-up. Never extend trust during rollback past an expired cutoff.
4. **Compromised current signing key:** stop any further compromised-key issuance using a separately approved owner-controlled incident process. The existing previous-key cutoff **does not** revoke a compromised *current* key. For urgent current-key compromise, new issuer/verifier configuration and immediate removal of compromised trust must be coordinated, potentially interrupting service. Do not claim that revoking refresh tokens or restarting a container alone revokes current access JWTs.
5. **Emergency session termination gap:** centrally revoking all refresh token families/account sessions and immediately denying active access JWTs across all resource services is **not implemented**. A reviewed token-version/session-epoch or bounded shared-denylist design, consistent authorization, database migration and tested cross-node enforcement are prerequisites. Never run unreviewed blanket SQL deletes or rotate customer credentials with this CI.
6. **Rollback/abort discipline:** use an explicitly reviewed previous artifact and its matching, still-trusted configuration, preserve every key expiry guarantee, and do not restore a known-compromised key or extend any previous-key cutoff. If synchronized rollout or owner/tenant verification fails, block new issuance and use the separately approved incident plan; do not silently roll back authentication. Retain exact commit/CI evidence, sanitized logs and the approval record.
7. **Release decision:** Stage45 `NO_GO`, open #242/#251/#255/#259, independent approval and nine runtime release certification gates still apply. The owner must explicitly authorize any real deployment, session migration or key retirement.

## Evidence and limits

B62-E already demonstrated synthetic real-container HTTP JWT verifier cases and a fail-closed issuer startup. B62-F adds unit-level refresh expiry and session-scope behavior, real signed JWT negative proof (stateless access stays valid), Python policy guards and an exact-HEAD CI workflow. It does **not** repeat the full Docker HTTP replay, prove real Postgres failover, implement an emergency global revocation endpoint, test trusted NTP across machines, or provide physical Windows/WSL2 certification. No real production keys or data are used. **NO_GO** remains until all independent owner/release gates close.
