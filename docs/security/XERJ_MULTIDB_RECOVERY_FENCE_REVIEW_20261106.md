# Aetheris multi-database recovery fence — review-only, disposable CI

**Parent verified checkpoint:** Draft PR #393 `dd83101ee5d459805a3c01c429351d997e8a0f85`, GitHub Actions #42196576778: 110 targeted Java tests, 90 live checks, User outbox data+schema PostgreSQL backup/restore and guarded rollback passed. This new child checks **application-level consistency across independently restored logical service databases**, not production recovery.

## Problem
Identity holds account-issued UUID tenant IDs; User holds tenant-owned records and stable transactional outbox events; Audit holds independently committed, deduplicated event receipts. Independent per-database PostgreSQL dumps are not a distributed atomic snapshot. A valid restore of every database can still produce an **invalid combination** of recovery points, resulting in missing Audit events or contradictory tenant ownership.

## Isolated proof
- A unique hosted GitHub Actions runner (the exact `xerj-mtls-ci-RUN_ID-ATTEMPT` Docker Compose project) provisions seven named **test-only databases inside one disposable PostgreSQL 16 container**: three original Identity/User/Audit logical service databases, three empty restored copies, and a separate old Audit snapshot for the mixed-recovery negative test. The application database `xerj_ci` and real-world databases are never used by this new script.
- Uses the **existing actual migrations**: Identity tenant migration, User tenant/outbox/dual-control migration, and Audit Flyway V1/V2. Synthetic account and User rows have a server-like UUID tenant ID; historical unowned rows remain NULL. One historic unowned Audit event has no outbox predecessor, as real legacy traffic can.
- Fixture first writes a matched event and fence A, captures an earlier Audit-only dump, then records a second synthetic persisted User+outbox created event and its matching Audit receipt. All three service databases are marked with fence B only after the fixture is quiescent. Two delivered outbox events are expected, and Audit must contain exactly the two matching event IDs/payloads and one legacy unowned event.
- Private PostgreSQL custom-format backups are taken **from each independent logical service database** under the same application-level fence B. Files stay in a private ephemeral runner temp directory and are SHA-256 checked before `pg_restore --single-transaction --exit-on-error` into three fresh databases. Source and restored states must satisfy identical fence markers, exact event identity/type/actor/tenant/name/email matching, persisted User records, matching tenant ownership and no pending/retry/leased/parked event backlog. No file bytes, hashes, secrets, JWTs or PII-shaped rows are uploaded.
- The **mixed recovery point** (current Identity and User but older Audit) must be denied even though the individual PostgreSQL restores succeed. This checks both fence mismatch and the absence of the second event receipt.
- A **forged tenant UUID** on a restored Audit event must invalidate the reconciled release candidate even if event counts and IDs still match.
- A **corrupted backup copy** must fail integrity matching against the in-memory source checksum. This is a local integrity check, not an authenticated, externally signed manifest.
- Preserve the prior Java authorization regressions, actual RSA/mTLS, two-account tenant controls, RabbitMQ publisher-vs-consumer identity, poison dead-letter routing, and the outbox rollback, operator dual-control, broker outage/recovery and ACK-gap audit idempotence checks. The exact PR commit must pass both CI jobs before a PASS claim.

## Clear NO_GO trust boundaries
1. The three logical databases are hosted inside **one disposable PostgreSQL instance**, not three independently replicated or geo-distributed production clusters. The fence is **simulated controlled quiescence**: no proof of live traffic coordination, isolation of in-flight transactions, or atomicity across real service databases. A client could race a fence in production without an enforceable global write freeze and event-drain protocol.
2. **RabbitMQ messages, in-flight deliveries, dead-letter custody, durable consumer offsets and broker quorum state are not preserved by PostgreSQL dumps.** The earlier live RabbitMQ tests are independent regression checks and do NOT make the backups a coherent broker/database recovery set. Audit matching is a release *precondition after quiescence*, not a general guarantee that `delivered` always immediately implies `audit_events` exists.
3. The fixture validates exact known event IDs and a strict empty active outbox at a checkpoint. It is not a general automated production reconciliation policy. Real deleted users, pending outbox rows, retries, historical event gaps, distributed IDs, multi-tenant memberships, clock skew and legal erasure require a separate risk-reviewed policy. No auto-replay or user-facing recovery endpoint was created.
4. Backup integrity is local SHA-256, not a signed attestation, tamper-proof backup, off-site encryption or authorized operator approval. Real backup key custody, checksum signing, RPO/RTO, WAL/PITR, audit evidence export and immutable incident records remain missing.
