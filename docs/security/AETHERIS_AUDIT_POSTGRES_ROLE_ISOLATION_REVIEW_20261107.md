# Aetheris Audit — PostgreSQL membership lock and role separation

**Branch:** child of exact-head verified draft PR #404 `8fc0f41566edf289571037a5316e9084cf77bfe1`. **Review-only; NO_GO for production.**

## The actual remaining data-integrity vulnerability

PR #404's opt-in cryptographic membership importer used the same application `JdbcTemplate` as the Audit event consumer. Even with a separately pinned RSA membership-authority signature, a compromised or misconfigured Audit process with `UPDATE` privileges on the local membership mirror could bypass that importer and self-grant `ACTIVE`. The system's true Identity/User authority and external monotonic recovery authority **remain unimplemented**. This child only closes a narrow database role-scope boundary in disposable integration and provides real code and migration building blocks for future owner-governed rollout.

PostgreSQL 16 requires **table UPDATE privilege** to use `SELECT ... FOR SHARE`, even when the code never writes the table (official PostgreSQL 16 "Privileges": https://www.postgresql.org/docs/16/ddl-priv.html). Granting an Audit listener direct membership `UPDATE` merely to retain PR #403's transactional row lock would be insecure.

## Actual code and schema changes

1. **Additive Flyway V4** `audit-service/src/main/resources/db/migration/V4__audit_membership_locked_admission.sql`: a small, deterministic, SQL-injection-free `SECURITY DEFINER` function `public.audit_membership_can_ingest(UUID, BIGINT, TIMESTAMPTZ)` that selects one existing membership row `FOR SHARE`, holding the row lock in the **caller's same transaction**, and returns a boolean if ACTIVE, matching tenant/user, valid revision and event time no earlier than `valid_since`. It uses *fully qualified relation names*, `SET search_path=pg_catalog,pg_temp`, and **REVOKE EXECUTE FROM PUBLIC**; it never inserts, updates, deletes, grants membership or executes dynamic SQL. Its owner must be a separately protected migration role.
2. **Real listener** `AuditLocalMembershipFence.enforce`: after RS256 event proof, ask that fixed function for a boolean. A missing, revoked or stale grant denies; a missing function/grant/JDBC outage propagates and **never accepts**. Existing `AuditEventStore.consume` `@Transactional` scope preserves the same local lock-and-effect serialization. No broker message can seed or update a membership row.
3. **Separate writer connection when explicitly enabled**: `AuditSignedMembershipImporter` now requires its own `AETHERIS_AUDIT_MEMBERSHIP_WRITER_DB_URL`, `_USERNAME`, `_PASSWORD`, with a PostgreSQL URL referring to the *same* Audit DB, an independent SQL role name, and a 32+ character password. It rejects missing/mismatched credentials and password provision while disabled. It uses a separate, unpooled `DriverManagerDataSource` **inside** the importer, avoiding a second global Spring DataSource bean that could replace the main Boot Audit datasource. Its pinned-key RS256 and SQL monotonic CAS logic from PR #404 remain unchanged. This does **not** grant an authoritative signer or network ingestion endpoint.
4. **Disposable PostgreSQL16 ACLs:** new CI script creates `xerj_audit_ingest` with SELECT/INSERT on `audit_events` plus *EXECUTE only* on the V4 locked-check function. It has **no SELECT, INSERT, UPDATE or DELETE privileges** on the membership table. Another independent `xerj_membership_writer` has only SELECT/INSERT/UPDATE on the membership table; it has **no read/write privilege on Audit events**, no membership DELETE, schema CREATE, superuser or database ownership. The existing fixture administrator is used for setup and independent observations only. All roles, secrets and grants exist solely inside the ephemeral Compose database.
5. **Real signed listener:** the inherited `run_xerj_real_signed_listener.sh` launches the actual packaged Spring Boot Audit JAR as `xerj_audit_ingest`, **never** as a fixture administrator. It strips the admin and membership writer passwords from the child process environment, and explicitly leaves the membership importer disabled in this running listener. No private signing key or privileged DB identity is handed to the live listener. The source publisher retains a separate RabbitMQ publish-only role.
6. `AuditPostgresRoleIsolationIT` proves with real PostgreSQL session principals: a correctly signed membership delta can be written under the writer role, the ingest role can execute the locked admission function inside a transaction but cannot mutate membership; it can durably store a User Audit event; the writer role cannot read, delete or inject Audit events; a later signed REVOKED update changes the admission decision; malformed shared/disabled JDBC configuration fails closed.

## What this does not prove, even with green CI

The two roles and the V4 function are strong scoped local database controls, **not a deployment permission**. A privileged DB owner, high-privilege migration role or improperly configured restore still has the ability to mutate/rollback both tables and the function. Do not infer an external anti-rollback witness or historical tenant authority. The cryptographic membership signer has not been linked to a real independently governed Identity/User membership source. It remains possible for a compromised authorized signer to attest false ACTIVE statements. A separately privileged signer/writer process must be isolated at the **process/workload** boundary too: placing both the Audit listener's and membership writer's credentials in the same process would undermine the isolation. The actual tested listener receives **only** the Audit ingest DB credentials and has `AETHERIS_AUDIT_MEMBERSHIP_IMPORT_ENABLED=false`. No real production reconciliation process is created or enabled here.

For a future production rollout, require independent authenticated authority service, workload identity and mTLS, separate worker/pod for the signed reconciler, strict DB grants with managed migrations, independently durable revocation watermark and witness, full snapshot reconciliations, monotonic recovery generation, controlled operator rotation of public keys, complete DLQ/inflight plan and reviewed recovery after restore. The actual Audit app's current HTTP read surface, global admin access, cross-cluster atomicity and authority freshness still require security review. Adding a `SECURITY DEFINER` function also creates an owner-trust obligation; it must not be owned by the application role or allowed to execute untrusted code.
