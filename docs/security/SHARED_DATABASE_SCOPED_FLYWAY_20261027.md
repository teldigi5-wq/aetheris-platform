# Shared physical PostgreSQL database — schema isolation rehearsal

**27 October 2026 · REVIEW DRAFT · NO_GO · not approved for production.**

This executable test follows PR #326's fresh separate-database Flyway proof and targets the biggest design uncertainty: existing Aetheris Compose defaults point Identity, User and Audit to a **shared physical PostgreSQL database**. Identity and User each carry a different version 1 migration. Running both in the same default schema and migration history would create conflicts or unsafe baseline assumptions.

A new synthetic single physical **PostgreSQL 16** database `shared_synthetic` is provisioned inside a disposable Docker container. The CI operator explicitly creates `identity_stage`, `user_stage` and reserved `audit_stage`. For the Identity and User services, each separate `currentSchema`, `SPRING_FLYWAY_SCHEMAS` and `SPRING_FLYWAY_DEFAULT_SCHEMA` points to **its own logical schema in the same database**. The real Java Spring/Flyway integration and Hibernate `validate` tests confirm that each V1 migration, Flyway history table, and service tables live exclusively in the intended namespace, with no public table collision. CI then inserts synthetic rows and reruns both service startups, checking that versioned migration histories remain exactly one row and data survives.

**Audit is deliberately NOT migrated in this stage.** The existing Audit service enables Flyway by default with `flyway_audit_schema_history` and `baseline-on-migrate: true`. That behavior requires a separate integration and independently reviewed policy before a shared-database rollout. There is no owner-approved path yet from any **historical existing schema** into these namespaced tables, no copy/ETL/data reconciliation, no tenant ownership mapping, and no shared-DB least-privilege user authentication proof. The synthetic Docker test connects using the database's **privileged** CI bootstrap account, not a genuine per-service production identity. It therefore proves namespace configuration and no public collisions only, NOT hard isolation against a compromised database client.

Never enable Flyway on a live shared database using these parameters without an owner/DBA-approved historical inventory, backup/restore, owner mapping and schema strategy; preserve production data. No protected-main merge, no live credentials, no actual production DB and no automatic deployment are touched. Stage45 release remains **NO_GO**; all nine certification gates and issue #242 remain unresolved pending physical owner evidence.
