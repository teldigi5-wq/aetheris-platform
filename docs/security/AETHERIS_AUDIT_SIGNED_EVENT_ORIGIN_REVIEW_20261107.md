# Aetheris Audit event origin authentication — opt-in RS256 service source

**Lineage:** stacked on verified draft PR #399, `a235e02f1b6df5a0ea0d3770a0d05a137c82d77b`. This child is a *real application code candidate* with explicit operational opt-in, not a release or completed recovery cutover.

## Threat and existing boundary

PR #399 fixes malformed Audit messages and same-event-ID conflicting replays in the real service. But those checks do not authenticate the **origin** of a new valid-shaped RabbitMQ event: a publisher that acquired publish access may invent a new `eventId` and tenant. Broker ACLs help restrict that access but are separate from cryptographic publisher authentication.

## Concrete application changes

1. `UserEventOriginSigner` (new actual User-service Spring bean) signs existing events with a **private RSA-3072+ PKCS#8 PEM**, JJWT **RS256**, explicit pinned key ID, fixed issuer/audience/subject, `jti=eventId`, event type, occurredAt, numeric user ID, name, email and exact optional canonical tenant UUID. A proof's lifetime is **300 seconds**. The proof is carried in a single `originProof` JWT member of the otherwise unchanged domain-event JSON. The signing key is never sent to Audit.
2. `UserEventPublisher`: direct legacy publishing signs **only if explicitly enabled**. Transactional outbox append remains unchanged and in the caller's writable User database transaction; no signature is written to the database at mutation time.
3. `UserOutboxRelay`: signs the event **at the actual publisher-confirm broker send**, when it has claimed the stable outbox event ID. This permits delayed parked/backlogged rows to receive a *fresh* short-lived proof rather than replay an expired JWS. The same event ID still deduplicates Audit after an ACK gap; a failure to sign marks the leased event as a bounded retry/parked item, not as delivered.
4. `AuditEventOriginVerifier` (new actual Audit-service bean): uses **only a pinned X.509 RSA-3072+ public key**. Before durable Audit storage, checks a valid **RS256** JWS signature; exact issuer, audience, key ID and subject; issue/expiry not exceeding 300 seconds; and immutable event ID, type, exact canonical timestamp, numeric user ID, name, email and tenant UUID. Missing, invalid, expired, tampered or incorrectly scoped proofs get sanitized `AmqpRejectAndDontRequeueException`, never writing to Audit.
5. `AuditEventStore` adds that verifier before repository insert. The previously implemented poison rejection and immutable event-ID collision checks stay in place. JDBC outages remain retriable rather than silently classified as poison.

## Explicit, separate operator switches (both OFF by default)

| Service | Environment variables | Purpose |
|---|---|---|
| User | `AETHERIS_AUDIT_ORIGIN_SIGN_ENABLED=true`, `AETHERIS_AUDIT_ORIGIN_PRIVATE_KEY_PEM`, `AETHERIS_AUDIT_ORIGIN_KEY_ID` | Enable signing; RSA-3072+ PKCS#8 private key present **only** with User publisher, injected through an approved secret manager |
| Audit | `AETHERIS_AUDIT_ORIGIN_VERIFY_REQUIRED=true`, `AETHERIS_AUDIT_ORIGIN_PUBLIC_KEY_PEM`, `AETHERIS_AUDIT_ORIGIN_KEY_ID` | Require signature using only the matching X.509 RSA-3072+ public key and pinned key ID |

Key material must be generated by an authorized owner, outside GitHub/CI logs, stored in an appropriately restricted secret manager, never checked into the repository. There is **no** silent default key, fallback to HMAC or acceptance of unsigned messages when required. Invalid/inconsistent opt-in key configuration is a startup error. Existing deployments remain unsigned **until explicitly migrated**; proof-bearing envelopes are rejected by intentionally disabled Audit verifiers rather than accepted as ambient trust.

**Operational dependency, not automated:** This is an incompatible trust-boundary change unless producer and consumer enablement are coordinated. Before any deployment, back up and inventory the real queue, configure and test an operator-only DLX, pause publishing, drain/retain historical unsigned messages under an approved disposition plan, deploy both sides atomically as far as operationally possible, and then resume. A mixed-version producer/consumer can quarantine legitimate events. There is **no zero-downtime claim**. Review clock skew, long-lived queues, redrives, key rotation, old-key expiry and expiry-based poison quarantine before enabling. The current single-key verifier does **not** provide overlapping-key rotation, and production staged rollout cannot be approved as-is.

## Verifiable acceptance

- `UserEventOriginSignerTest`: genuine ephemeral RSA-3072 proof, JJWT claim verification, direct publisher, outbox relay send after lease and stable event IDs, malformed key/claim configuration denials.
- `AuditEventOriginVerifierTest`: actual RSA public-only cryptographic verification before repository insert, valid canonical/legacy messages, denial of unsigned, wrong key, wrong kid/issuer, expired and tampered tenant/user data without writes, plus retryable database failure.
- Existing Java JWT/mTLS/tenant/auth/audit/outbox regressions and real RabbitMQ4/PostgreSQL16 outbox, poison DLQ, restore, replay and witness tests must pass on the **exact child HEAD**. The workflow uses only ephemeral isolated CI secrets and never enables production switches.
- This is not a complete cross-deployed real broker integration with both signing and verification switches active; test-side crypto interoperability and source wiring must not be overstated.

## Known omissions — remain NO_GO

This binds a message to a **private-key holder**, but still does **not** prove the User mutation's authorized resource owner, tenant membership at replay time, a recovery epoch, a non-rollbackable witness, live old-primary fencing, exactly-once semantics or currently valid service credentials after key compromise. Its verifier has one pinned key; no deployed rotation/revocation/dual-key window has been proven. A holder of the private key can forge arbitrary new, valid signed IDs; ensure least-privilege workload and key lifecycle before production. Key compromise requires out-of-band rotation and quarantine review. The default-disabled feature does **not close** the production-origin vulnerability.

XERJ contribution issue #360 is separate: **2/6 stages fully complete, four formal stages remain**, with genuine human privacy/history, licence/attribution, formal manifest counts/approval and upstream maintainer review outstanding. **No source repin or XERJ submission** here. Aetheris Platform #251 and Runtime #23 remain OPEN; Stage 45 production release is **NO_GO** with nine independent external attestations historically missing.

**Decision:** retain this PR draft/unmerged, only preview evidence from GitHub Actions, never enable both switches or issue production keys without explicit operator approval and a reviewed deployment runbook. This PR changes real code, not production runtime.
