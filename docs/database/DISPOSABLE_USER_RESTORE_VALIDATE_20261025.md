## Actual experiment

`tests/security/docker-compose.pg-recovery-overlay.yml` overlays the already tested isolated 8-service Compose test topology to add two more copies of the **same exact User runtime image** and a third restricted Python probe container. The two extra applications point to separate disposable databases `aetheris_restored` and `aetheris_drift`, both with **`SPRING_JPA_HIBERNATE_DDL_AUTO=validate`**. They have no published ports, host networking, persistent database volumes, production credentials, or Docker socket access.

The independent `user-service` source instance on a separate, fresh temporary PostgreSQL 16 database remains `ddl-auto=create` **only to seed a brand-new synthetic schema**. After rechecking the **26** previous JWT assertions and **30** previous numeric-ownership-denial assertions, a signed synthetic ADMIN sends `POST /api/users` to insert exactly one inert record. The test then:

1. Uses **real PostgreSQL `pg_dump -Fc`** and verifies an archive is nonempty; `pg_restore --exit-on-error` restores it into a new database. A second independently restored clone receives `ALTER TABLE users DROP COLUMN email` as the negative-control drift.
2. Takes text dumps of restored database schema and data before launching any validation-only app.
3. Starts the actual User Spring Boot image against the **restored** database with `ddl-auto=validate`. Through independent signed HTTP checks, verifies the synthetic row, valid ADMIN access, DENY (403) for DEVELOPER/API_CONSUMER and DENY (401) for expired or tampered Identity-issued tokens.
4. Dumps restored schema/data again and requires **byte-identical comparisons** to the pre-start text dumps. A validation-only application must not silently modify the restored database.
5. Starts the same image against the **drifted clone**, requiring nonzero startup exit and an explicit Hibernate **missing `users.email` column** error, not a generic failure such as an unreachable database.
6. Always destroys the entire experiment Compose stack, all containers, networks, PostgreSQL archives and temporary data. No production volume is mounted or altered.

Only GitHub Ubuntu CI is used because of the disposable Docker environment. The images are built from the exact PR head. No public port or external endpoint is accepted by the test-only probes.

## Interpretation / outstanding issue #242

A passing run demonstrates **only** that a clean synthetic schema generated by this User image can be backed up and restored with PostgreSQL tools, then validated by the same source image, while one deliberately drifted schema fails closed. It does **not** verify a real historical Hibernate schema, represent production recovery SLAs, or prove backward compatibility with live records, application upgrades or multi-service Flyway ownership. It does **not** replace six Compose `ddl-auto:update` overrides or integrate new migration SQL.

Before updating production Compose, independently inspect sanitized real metadata using PR #246 inventory tooling, approve a per-service versioned Flyway plan (reconcile #247 with current platform release candidate), back up and restore-test a **representative authorized nonproduction copy** of the existing database, and test mixed-version startup/concurrent deployments. Then require explicit human approval and a rollback/cutover plan. Existing persisted volumes must be preserved.
